# Историческая проверка действий для SKU

Модуль `shared/ecommerce/` строит оценки **последствий конкретных действий** и передаёт их обычному ядру MCDA. LLM для импорта, расчёта и backtest не требуется. Реальный обезличенный датасет ещё не предоставлен; примеры полностью синтетические.

## Воспроизводимый пример

Из корня проекта:

```powershell
npx tsx scripts/generate-ecommerce-demo.ts
npx tsx scripts/run-ecommerce-backtest.ts --input data/ecommerce/synthetic-monthly.csv --mapping data/ecommerce/mapping.json --config data/ecommerce/backtest-config.json --out ecommerce-report.json
```

Генератор создаёт 3 SKU × 48 месяцев (2021–2024), Mulberry32, seed 42. Синусная сезонность, тренд и вариация продаж заданы для демонстрации, причинные эффекты действий не имитируются. JSON-отчёт содержит SHA-256 исходного CSV, маппинг, конфигурацию, допущения, каждую постановку, результаты четырёх режимов и наблюдения test. Повтор с теми же файлами и seed воспроизводит результат. Выходной файл может содержать коммерческие данные при работе с настоящим CSV.

## Импорт и доступность

Обязательны SKU, дата и неотрицательные продажи в штуках. Поддерживаются даты `YYYY-MM`, `YYYY-MM-DD`, `DD.MM.YYYY`, `MM.YYYY`; невозможные календарные даты не принимаются. Период агрегации задаётся явно: `day`, `week` (понедельник), `month`. CSV читается как данные, с ограничениями размера и числа строк. Маппинг задаётся пользователем; найденные синонимы — предложение, требующее проверки.

Внутри периода продажи и денежные потоки суммируются, цена и себестоимость усредняются, остаток берётся по последней дате. Если цены нет, она может быть рассчитана как выручка / продажи в этом же периоде. Семантику полей нужно согласовать с поставщиком данных: себестоимость — за единицу, остаток — на конец периода, денежные поля — в одной валюте. Отрицательные числовые значения отклоняются; чистые продажи с отрицательными возвратами требуют предварительного преобразования.

Для построения задачи доступные поля определяются по выбранному train SKU. Заполненность столбцов во всём файле используется только как справка. Недоступные действия/критерии возвращаются с причинами исключения. Пропуски периодов обозначаются `gap`; окна train/test с ними отклоняются, поскольку отсутствие наблюдения не означает нулевые продажи. Некорректные даты и строки без продаж пропускаются с отчётом парсера; это может привести к отклонению окна.

## Действия и критерии

Доступны увеличение/сохранение/сокращение закупки, снижение цены, дополнительное продвижение и вывод из ассортимента. Набор настраивается через `actions`. Спрос, поставка, запас и продажи моделируются отдельно для каждого действия. Модель использует одну поставку за горизонт; приход после горизонта на продажи не влияет. При неизвестном начальном запасе продажи моделируются без ограничения запасом; критерии запасов отключены. При отсутствии цены/себестоимости прибыль отключена. Нельзя трактовать «сохранить» как точное повторение исторических заказов: здесь это явно заданная политика пополнения до прогноза спроса с учётом срока поставки.

| Критерий | Направление | Единица |
|---|---|---|
| Валовая прибыль после дополнительных затрат | max | руб. |
| Неудовлетворённый спрос | min | доля |
| Риск дефицита | min | вероятность |
| Покрытие остатком на конец | min | периодов |
| Капитал в запасах | min | руб. |
| Хранение | min | руб. |
| Оборачиваемость | max | раз |
| Потери от возвратов | min | руб. |

Формулы и необходимые поля находятся в `ECOM_CRITERIA` в `actions.ts` и переносятся в `DecisionProblem`. Например, минимизация покрытия остатком означает предпочтение меньшего избыточного остатка при одновременном учёте дефицита другими критериями. Это выбор модели, который нужно согласовать с бизнес-задачей. Возвраты показаны отдельным критерием, а не вычтены из валовой прибыли.

Все параметры последствий сохраняются в `metadata.ecommerce.assumptions`: эластичность, рекламный uplift, скидки, стоимость хранения при отсутствии наблюдений и срок поставки при отсутствии данных — экспертные допущения. Равные точные веса и границы `[0.5/n, min(1, 2/n)]` по умолчанию также маркируются как экспертное допущение. Пользователь может задать собственные веса; неверная сумма не исправляется автоматически. Построенная интерактивная задача имеет статус `draft` для проверки пользователем.

## Временной протокол и неопределённость

`first_test` — первый период, недоступный при принятии решения. Train включает ровно `train_periods` предшествующих периодов. После каждого окна cutoff увеличивается на `step`; `last_test` — включительно последний допустимый cutoff, а не конец последнего test. Если он не задан, берётся последний полный test в файле. Все окна должны иметь полную историю.

Показатели спроса используют последние `window` периодов train. Сезонные месячные индексы рассчитываются только по train при наличии минимум `seasonality_min_years` лет. Цена, себестоимость, реклама, возвраты и последний остаток также берутся из train. Сроки поставок ресемплируются из train. Будущие названия и категории не передаются в постановку. Это протокол по дате наблюдения: поставщик данных должен гарантировать, что строки и их ревизии действительно были доступны на cutoff; отдельного времени публикации в текущем контракте нет.

Для оценок действий используется bootstrap спроса с возвращением, с удалением/восстановлением сезонности. Общие случайные числа применяются ко всем действиям. Это модель независимых периодов; автокорреляция и структурные сдвиги не моделируются. По умолчанию диапазон последствий — `[q10, q90]`, точка — медиана; риск дефицита — доля траекторий с дефицитом. Затем ядро использует явно заданное равномерное распределение в интервале (настройка ядра по умолчанию); такой интервал не сохраняет всё bootstrap-распределение и зависимости критериев. Параметры и распределения входят в результаты ядра. Режимы M/W меняют только неопределённость оценок и весов в одной постановке; выборки исходных последствий одинаковы.

Backtest сначала строит задачу, интервалы и рейтинг, затем читает test для оценки. Каждый режим возвращает pBest/pWorst, ранги и score. Forecast — медиана bootstrap суммарного базового спроса без эффекта действия. Наблюдения — продажи, полная выручка и валовая маржа (если все необходимые значения присутствуют), журнал фактических действий при наличии. Пропущенные денежные значения не превращаются в нули.

Ошибки вычисляются относительно наблюдаемых продаж: signed = forecast − actual, MAE, RMSE, WAPE = сумма абсолютных ошибок / сумма абсолютных продаж; при нулевом знаменателе WAPE = null. Покрытие интервала — доля окон, где продажи попали в прогнозный диапазон. При перекрывающихся test-окнах ошибки зависимы; метрики описательные. Отчёт ограничен 100 окнами, миллионом mode-итераций и двумя миллионами bootstrap-периодов.

**Backtest не доказывает оптимальность управленческих действий.** Спрос сравнивается с продажами как прокси; дефицит цензурирует продажи, а изменения цены/рекламы нарушают сопоставимость. История не содержит наблюдений для невыполненных альтернатив. Даже при наличии журнала действий причинный эффект не идентифицируется автоматически: нужны эксперимент или обоснованная причинная модель.

## API

Все маршруты находятся под `/api/v1/ecommerce`, используют общие ограничения загрузки и `API_TOKEN`, если он включён.

| Маршрут | Вход / результат |
|---|---|
| GET `/demo-dataset` | Синтетический CSV |
| POST `/inspect` | `{content}` → заголовки, пример строк, поля, предложенный маппинг |
| POST `/mapping` | `{content, mapping, period}` → статистика, предупреждения, SKU, справочная доступность |
| POST `/problem` | Предыдущие поля + `sku, cutoff, train_periods?, window?, config?` → черновик задачи, признаки, допущения, исключения |
| POST `/backtest` | `{content, mapping, period, backtest, config?}` → полный JSON-отчёт |

`backtest` соответствует одноимённому объекту в `data/ecommerce/backtest-config.json`, `config` соответствует `problem` в CLI-конфигурации. Для запуска расчёта интерактивного черновика используется существующий POST `/api/v1/runs`. Сохранять ответ backtest следует отдельно: endpoint возвращает отчёт, но не помещает его в хранилище обычных экспериментов. Экран `/lab#ecommerce` поддерживает CSV, демо, маппинг, выбор действий и временных окон, построение черновика и backtest. Для прикладной апробации необходим реальный обезличенный CSV и согласование полей, временной доступности и допущений.
