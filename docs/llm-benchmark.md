# Эксперимент по качеству формализации LLM

`shared/llm-eval/` определяет контракт корпуса, метрики и проекции фактов. `server/llm-eval/runner.ts` выполняет запросы через существующий `LlmService`. Один и тот же prompt, формат ответа, параметры генерации, валидатор и преобразователь черновика применяются ко всем провайдерам. Рейтинг в этом эксперименте не рассчитывается: исследуется качество извлечения входных данных при неизменном математическом ядре.

## Корпус и эталоны

`data/llm-benchmark/cases.json` содержит 36 синтетических постановок: 12 типов × 3 контекста (поставщики, облачные платформы, экспертные сценарии действий для SKU). Типы: точные данные, интервалы M, интервалы W, пропуск оценки, неизвестные веса, порядок важности, пороговое ограничение, исключение альтернативы, связный текст вместо строк, необычное явно заданное направление оптимизации, prompt injection, несовместимая сумма точных весов. Десятичная запятая, проценты и веса в долях встречаются в разных типах.

Каждая запись содержит текст, `gold: DecisionProblem`, семейство, теги, заранее заданные алиасы критериев и ожидаемую готовность к расчёту. Пропущенные оценки имеют `kind: missing`, неизвестные веса — элемент без чисел. Эталон сохраняет несовместимую сумму весов вместо её исправления. В случаях с исключением из двух альтернатив остаётся одна: текущее ядро требует минимум две, поэтому `expected_run_valid=false`. Случаи с пропуском оценки также не готовы к расчёту. Эти отрицательные примеры нельзя исключать из знаменателя метрик.

Эталоны построены из явных спецификаций в `scripts/generate-llm-benchmark.ts`, независимо от `heuristicDraft`, ответов моделей и `buildProblemFromDraft`. Скрипт позволяет воспроизвести JSON; изменения в разметке следует проверять до сравнения моделей. Это корпус с общими шаблонами, а не 36 независимых реальных запросов и не независимая ручная разметка. Для научного обобщения нужны отдельные реальные постановки, экспертная проверка эталонов, разделение по семействам и повторные прогоны моделей. Gold и алиасы не передаются провайдерам.

## Два уровня оценки

Существующая формализация просит LLM вернуть JSON извлечения (`alternatives`, `criteria`, `evaluations`, `weights`, `weight_order`, `constraints`), а затем преобразует его в `DecisionProblem`. Benchmark сохраняет этот формат; `DraftResponse` в `shared/llm-eval/schema.ts` — его проверяемый контракт.

Исходный ответ оценивается до фильтра трассируемости. Отдельно сохраняются очищенная постановка, результаты её валидации, удалённые галлюцинации, неизвестные поля и журнал преобразований. Улучшение после фильтра не выдаётся за качество модели. В частности, число, присутствующее в исходном тексте у другой альтернативы, может пройти фильтр трассируемости, но ошибочная привязка всё равно даёт FP/FN относительно gold.

Отдельные показатели валидности:

- `strict_json_valid`: весь ответ разбирается стандартным `JSON.parse`, без удаления Markdown и поиска JSON внутри текста.
- `recovered_json`: стандартный парсер не смог разобрать ответ, но общий `parseJsonReply` извлёк JSON. Это не повышает долю строгого JSON.
- `draft_schema_valid`: извлечённый объект соответствует формату ответа. Лишние поля, включая рейтинг, отклоняются.
- `problem_schema_valid`: сформированный `DecisionProblem` соответствует его структурной схеме.
- `semantic_valid` и `run_valid`: результаты штатного валидатора без/с `forRun`. Первая проверка допускает неполный черновик, вторая проверяет готовность к вычислениям.
- `run_validity_accuracy`: совпадение готовности с gold. Отказ провайдера/невалидный формат не засчитывается как корректное распознавание отрицательного примера.

Структурно валидный пустой черновик может не содержать ни одного правильного факта. Поэтому валидность не заменяет показатели точности извлечения. `status=ok` означает, что ответ удалось разобрать и проверить по формату извлечения; это не означает совпадения с gold или готовности к расчёту.

## Сопоставление фактов

Факты разбиты на альтернативы, критерии, направления, единицы, оценки, веса, порядок важности и ограничения. Идентификаторы модели разрешаются через названия сущностей, поэтому смена ids не ухудшает оценку. Названия приводятся к NFKC, нижнему регистру, единому пробелу и `е` вместо `ё`. Допускаются только алиасы критериев из эталона; нечёткий поиск или дополнительная LLM для сопоставления не применяются. Единицы сравниваются буквально, автоматического пересчёта валют/масштабов нет.

Числа совпадают при `|pred − gold| ≤ 1e−6 + 1e−6 × |gold|`. Веса с явно указанной единицей `percent` переводятся в доли делением на 100; повторной нормировки нет. Точная оценка и интервал — разные факты даже при одинаковых границах. Интервал сравнивается целиком с проверкой обеих границ и привязки к паре альтернатива/критерий. Дополнительная точечная оценка внутри интервала учитывается как отдельный факт. Нижние/верхние границы и точечное значение веса оцениваются отдельно. Контекст, формулировки вопросов, цитаты и служебные настройки ядра не входят в F1.

Совпавший факт даёт TP; лишний/неправильный — FP, отсутствующий — FN. Дубликаты не могут повысить TP: повтор становится FP. Неверное значение по нужной паре даёт и FP, и FN. Precision = TP/(TP+FP), recall = TP/(TP+FN), F1 = 2TP/(2TP+FP+FN). Нулевой знаменатель возвращает `null`. Отчёт содержит показатели каждого случая, micro-метрики по всем фактам и по группам, а также долю полного совпадения.

`unsupported_facts` — лишние альтернативы, критерии, оценки, веса, отношения и ограничения относительно эталона. Ошибки направления/единицы показаны как FP соответствующих групп, но не включены в этот счётчик. Расхождение не доказывает намеренного выдумывания; при неполной разметке эталона возможны ошибки разметки. Для ответов, не прошедших схему, извлечение фактов не выполняется: они получают FN всех gold-фактов, но число дополнительных фактов неизвестно. Число таких случаев (`facts_unscorable_cases`) показывается отдельно, чтобы отсутствие оценённых галлюцинаций не трактовалось как их отсутствие.

## Запуск

Из корня проекта, без ключей и сети:

```powershell
npx tsx scripts/run-llm-benchmark.ts --providers mock --out results/llm-mock-run1
```

`mock` — существующий детерминированный парсер по правилам, не языковая модель и не oracle с доступом к gold. Даже если `.env` выбирает облачного провайдера по умолчанию, CLI без `--providers` использует только mock.

Для отдельного сравнения настроенных моделей:

```powershell
npx tsx scripts/run-llm-benchmark.ts --providers openai,yandexgpt,ollama --repeats 3 --max-tokens 6000 --out results/llm-models-run1
```

Параметры подключения читаются существующими адаптерами из серверного окружения / `.env`: `OPENAI_API_KEY`, `OPENAI_MODEL`, `YANDEX_API_KEY` или `YANDEX_IAM_TOKEN`, `YANDEX_FOLDER_ID`, `YANDEX_MODEL`, `OLLAMA_BASE_URL`, `OLLAMA_MODEL`. Альтернативный локальный провайдер — `llamacpp`, параметры `LLAMACPP_BASE_URL`, `LLAMACPP_MODEL`. Сами секреты в отчёт не включаются. Удалённые обращения используют соответствующие квоты/тарифы; в рамках реализации выполнен только mock-прогон.

Настройки по умолчанию: temperature=0, maxTokens=6000, один повтор. `--cases` задаёт другой JSON-корпус. `LLM_MAX_RETRIES` применяется одинаково ко всем провайдерам, число попыток сохраняется. Fallback принудительно выключен независимо от `LLM_FALLBACK`. Перед первым запросом проверяются структура корпуса и согласованность `expected_run_valid` с штатным валидатором. Провайдеры вызываются последовательно в порядке списка для каждого случая и повтора; порядок не рандомизирован, сравнение времени описательное.

Каждый запуск требует **новый каталог** `--out`, чтобы исключить перезапись предыдущего эксперимента. Содержимое:

- `responses.jsonl`: полный ответ, parsed-структура, метаданные вызовов, ошибки, raw/processed-метрики и очищенная постановка; запись после каждого случая позволяет сохранить завершённые ответы при прерывании.
- `report.json`: общий паспорт, полный корпус, хеши корпуса/prompt/схемы, шаблон инструкции, схема ответа, версии приложения/ядра, настройки, сведения о моделях, все строки и сводка.
- `summary.json`: компактная сводка для сравнения провайдеров.

Время `elapsed_ms` включает повторы и преобразование ответа; отдельные latency/usage сохраняются для каждой попытки. Стоимость оценивается существующим сервисом только при известных usage и явно настроенных `*_PRICE_INPUT_PER_1M`, `*_PRICE_OUTPUT_PER_1M`, `*_PRICE_CURRENCY`. Валюты не суммируются между собой, неизвестная стоимость не превращается в ноль. У mock токены приблизительно оцениваются по длине текста, а цена неизвестна.

CLI завершает весь набор, сохраняя ошибки отдельных провайдеров. Код возврата 1 означает наличие сетевых/форматных ошибок; низкая F1 или ожидаемая неготовность постановки сами по себе не являются сбоем запуска. Версии удалённых моделей, время, стоимость и request_id могут изменяться; temperature=0 и seed математического ядра не гарантируют идентичности ответов LLM. Паспорт фиксирует доступные версии моделей и все реальные настройки.

## Проверка реализации

```powershell
npm test
npm run build
```

Тесты проверяют все 36 эталонов, числовую погрешность, независимость от ids, интервалы, дубликаты, неизвестные значения, два тестовых провайдера на одинаковых запросах, отсутствие gold в prompt, запрет fallback, ошибки/Markdown JSON, сохранение галлюцинаций в raw-метриках после фильтра и полный офлайн-прогон. Реальные платные API тестами не вызываются.

## Лаборатория и HTTP API

На `/lab#benchmark` можно загрузить контрольные случаи, выбрать модели и запустить сравнение либо открыть JSON-отчёт CLI. `GET /api/v1/llm-benchmark/cases` возвращает корпус. `POST /api/v1/llm-benchmark` принимает `{providers: ["mock"], case_ids: ["sourcing-exact"]}` и возвращает полный отчёт. К endpoint применяются API_TOKEN, лимит размера JSON и ограничение частоты LLM-маршрутов; одновременно выполняется один HTTP-пакет на процесс. Сравнение использует те же настройки и раннер, что CLI. HTTP-запуск имеет один повтор, максимум 36 случаев и 5 провайдеров. Отчёт нужно скачать: он не сохраняется в историю MCDA-экспериментов. Для долгих прогонов предпочтителен CLI с сохранением промежуточных ответов.
